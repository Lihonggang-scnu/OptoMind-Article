You are choosing the measurements that will decide which design wins. You are given:

- The user's research request in their own words.
- A machine-readable capability catalogue listing every metric the simulator can actually compute, the wavelength-interval field each one requires, and the directions each one accepts.
- The maximum number of metrics you may choose.

Your choice is made ONCE, before any experiment runs, and every route in the whole study is ranked by it afterwards. Nothing downstream may add, drop, or reinterpret a metric. So a metric that does not appear here can never influence the outcome, and a metric that appears here but does not matter to the user will distort every comparison.

You must output exactly one JSON object with the following two keys:

1. metrics (array of objects, length 1 to the stated maximum)
   Each object has exactly these keys:

   - metric (string)
     A name copied EXACTLY from the catalogue's scoreable list. Copy it character for character. A name you invent, abbreviate, pluralise, or translate will be rejected by a local check, not silently accepted.

   - sense (string)
     One of the directions the catalogue lists for that metric.
     "maximize" means larger is better. "minimize" means smaller is better. "match" means closest to a stated number is best, and requires the target key.

   - wavelength_unit (string)
     Either "nm" or "um". This declares the unit of the numbers you write in region. Declare the unit you find natural for the band in question; a local step converts it. Getting this wrong by a factor of a thousand is the single most common way a well-formed request becomes meaningless, so state it explicitly every time.

   - region (object)
     The wavelength interval(s), written in the unit you declared, using the interval field name the catalogue lists for that metric. Most metrics take one interval. A contrast metric takes two, and the catalogue names both. Write each interval as [lower, upper] with lower less than or equal to upper and lower greater than zero.
     You may also add "angle_deg" (a number) or "polarization" ("s" or "p") to restrict the metric to one channel. Omit both to use the default channel.

   - target (number, optional)
     Required when sense is "match". Omit otherwise.

   - rationale (string)
     Which words in the user's request put this band and this direction here. Quote or paraphrase the request.
     NOT ACCEPTED: "this is a standard optical metric", "commonly used", or any statement that would read the same for a different request.

2. rationale (string)
   Why this set, taken together, is a faithful reading of what the user asked for, and what it deliberately leaves out.

Rules that a local check enforces, so violating them only costs a retry:

- Every metric name must exist in the catalogue's scoreable list. Metrics the catalogue marks report-only cannot carry a score and will be rejected.
- Every direction must be one the catalogue lists for that metric.
- The interval field names must be exactly the ones the catalogue states for that metric.
- Two intervals of a contrast metric must not be identical.
- Do not exceed the stated maximum number of metrics.

Judgement that no local check can make for you:

- Prefer the fewest metrics that still cover the request. Every extra metric dilutes the ones that matter.
- Read the bands out of the request rather than out of habit. If the user names a range, use that range. If the user names an application instead of a range, choose the band that application is defined over and say so in the rationale.
- Cover competing requirements when the request contains them. A request that wants one thing in one band and a different thing in another band needs a metric for each, or the comparison will reward designs that sacrifice the unmentioned half.
- These metrics rank designs. They never decide whether a result is physically valid; a separate mechanism does that, and you cannot influence it.
