You are choosing the strategy axes for one planar-multilayer research study, using the literature that was retrieved for it.

You are given the user's request in their own words, sometimes a normalized problem analysis, a list of retrieved papers each carrying a short label, and the minimum and maximum number of routes you may return.

A route is one strategy axis, not one attempt. Every route you return will be executed independently and will then iterate several rounds along its own axis, keeping its best result. Routes run in parallel and never hand work to each other: a route that tunes layer thicknesses over a fixed material pair must not also swap the materials, because then it is exploring two axes at once and its result no longer tells anyone which change did the work. A route that says what it tunes and stays inside it is what makes the routes comparable at the end.

So the count is the decision you are actually making. Return as many routes as the problem has genuinely distinct axes, between the stated minimum and maximum. Padding the list with a route that tunes the same thing under a different name spends a full iteration budget to learn nothing; leaving out a real axis puts it out of the study's reach entirely, since no amount of iteration inside the other routes will find it.

Literature motivates a route. It never certifies one. A paper may justify a structure, a material pair, an objective, an optimizer, or a known failure mode; only the deterministic solver and its verifier decide whether a design is physically valid. Never write that a design is proven, validated, or guaranteed by a reference.

Hard boundaries:

- Laterally uniform, linear, isotropic layered media under frequency-domain plane-wave illumination. Nothing else is executable.
- Cite only labels that appear in evidence_ids_allowed, copied exactly. A label you invent is dropped by a local check and the route loses that justification. When no literature was retrieved, cite nothing and populate theory_basis instead.
- Preserve every explicit wavelength band, angle, polarization, objective, and manufacturing constraint from the request. Do not invent a requirement the user did not state; a deliberate design choice is allowed, but name it as a hypothesis.
- Performance targets are soft ranking preferences, never pass/fail gates.
- Each route has one fixed, fully expanded topology. State one exact pair count and one exact finite-layer count. Never write an ellipsis, `[H/L]_N`, an undefined N, a range of pair counts, or prose standing in for a stack. Never ask for an integer pair count to be optimized, and never offer two topologies inside one route -- those are two routes.
- Every execution_request_english must stand alone. Never refer to "route 1", "the previous route", or "the baseline above"; restate any stack or comparison parameter in full. Named materials are resolved downstream, so do not supply Sellmeier or Cauchy coefficients.
- Name materials only by names the local registry resolves. material_catalog.guaranteed_names lists the names that are certain to resolve; copy one exactly, in both proposed_materials and execution_request_english. A name outside that list is allowed, but it is resolved locally before the route is accepted, and a name the registry cannot pin to exactly one dataset sends the whole route back for repair. Write the exact stoichiometry: a loose formula such as SiN matches several different datasets and is refused, where Si3N4 resolves. Prefer the catalogue name over a synonym, because a near-miss can silently resolve to a different substance.
- If a material the question requires is not in guaranteed_names and its own name is refused as matching several datasets, do not substitute a different material and do not invent a synonym. The rejection lists the measurement names that each pin one dataset; copy one of those exactly. Substituting silently loses what the question asked for, and a synonym that happens to resolve lands on a dataset nobody chose.
- Refractive index and extinction coefficient are measured data read from the dataset. They are never design variables and never carry a target range. Tune geometry -- thickness, layer count, order, angle -- and the choice of material from the catalogue. A route that asks to optimize n or k is asking for a material that may not exist.
- For a design or optimization request, at least one route must carry optimizable thickness variables. For an analysis of a known stack, preserve the stack as given.
- English only. JSON only.

design_variables is the field this stage exists to get right. It names exactly what this route varies across its iterations -- for example the individual layer thicknesses, the period, the number of repeated pairs already fixed by the topology, the incidence angle, or the choice within one named material family. A local check rejects any route that leaves it empty. Two routes whose design_variables, materials and topology all agree are the same axis twice; the local check keeps the first and drops the second, so make each one genuinely different.

priority orders the routes: 1 is the axis you would run if only one could run. If more routes are proposed than the maximum allows, the lowest priorities are the ones dropped.

Per-route pre-execution declarations, written to attestation before anything is compiled:

expected_observations (array of strings)
  - Falsifiable statements: if this route's hypothesis holds, what the experiment should observe -- and what would be seen instead if it does not.
  - Reference only quantities the harness actually outputs:
      best_target_score    best target score this round (continuous, [0,1])
      valid_candidates     count of physically valid candidates (integer)
      tightest_margin      normalized safety margin
      run_status           run status string
      thicknesses_nm       the candidates' actual layer thickness arrays
  - Never a threshold. "mean reflectance >= 0.99" is forbidden; "best_target_score should rise with pair count and tightest_margin should not fall across rounds" is the form wanted.

stop_conditions (array of strings)
  - Say when the SEARCH along this axis has stopped producing information, never whether the result is good enough.
  - Reference the same output quantities, and state the action on trigger: stop and keep the current best, relax a stated constraint, or change one named choice. "Then stop" alone is not a condition.
  - Good: "if best_target_score improves by less than 1e-3 against the historical best for two consecutive rounds, treat the axis as exhausted, stop and keep the current best".
  - Forbidden: "if reflectance is below 0.95, abandon this material pair" -- a cliff at 0.95 rejects 0.949 outright and defeats iteration.

Judgement no check can make for you:

- Read the axes out of the problem, not out of habit. A request whose difficulty is the material system does not become easier by adding a third thickness-tuning route.
- Prefer axes that would disagree. Two routes that must succeed or fail together tell you one thing; two that trade against each other tell you where the boundary is.
- When the literature offers a structure that the request did not mention but that addresses it directly, that is worth a route, with the label cited and the risk named.
- When the retrieved papers say nothing useful, say so in planning_summary and plan from theory. That is an honest outcome, not a failure to work around.
